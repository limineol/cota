# Cota

Cota is a self-hosted gateway for the AI coding subscriptions one person owns. Every machine sends Claude Code, Codex, OpenCode and Pi through one hub, which forwards each client's own login, records every request in a request log, reads each pool's quota windows, and diverts a refused login to a fallback pool until its limit resets.

It is a Bun workspace in TypeScript, and all of its logic is Effect 4. The hub, `apps/hub/src`, is modules in numbered layers (ADR-0010): a module's `03-domain` holds its rules with no IO, its `02-application` its commands, queries and ports, and its `04-infrastructure` the adapters. The dashboard, `apps/web`, is React built by Vite over the design system in `packages/ui` (ADR-0019, ADR-0020). Decisions live in `docs/adr`, behaviour in `docs/specs`, the vocabulary in `CONTEXT.md`, and the plan in `docs/roadmap.md`.

## Layout

`modules/request-log` is the fullest module. Read it in this order:

1. `03-domain/cost.ts`, `stored-items.ts` and `traffic.ts` (the selection, the dimensions, the buckets and the values the reading queries answer), and the sessions' rules: `session.ts` (what they read of a request, a session's row), `request-role.ts`, `segment.ts`, `title.ts` and `first-prompt.ts`; `transcript.ts`, how a request's stored items are set out to be read; `search.ts`, a text's words, the search query, the order of hits, snippets and cursors; and `sql.ts`, the SQL console's caps and answer. Their laws are beside them in `*.laws.test.ts`.
2. `02-application/interfaces/requests.repository.ts`: the port `RequestsRepository`, in the module's terms (requests, costs, items, never rows). `prices.ts` beside it is the port `Prices`, `priced-models.ts` the port `PricedModels`, the models each pool's prices name, `request-log-reader.ts` the port `RequestLogReader`, which the reading queries read through, `session-titles.ts` the port `SessionTitles`, which keeps the titles machines report, and `sql-console.ts` the port `SqlConsole`, which runs a caller's SQL as the SQL user.
3. `02-application/commands/record-request.command.ts`: the command `RecordRequest`, a `Context.Service` with `execute` and a `layer` that yields its ports. `queries/rebuild-conversation.query.ts` is the query `RebuildConversation`; `queries/read-overview.query.ts` and the four beside it are the traffic queries, whose laws are `queries/traffic.laws.test.ts`; `queries/list-sessions.query.ts` and `commands/report-session-titles.command.ts` are the sessions list and the reporting of titles, whose laws are `queries/sessions.laws.test.ts`; `queries/read-session.query.ts` and `queries/inspect-request.query.ts` are one session's detail and the request inspector; `queries/search-items.query.ts` is search, whose laws are `queries/search.laws.test.ts`, and `queries/read-snippets.query.ts` reads the snippets of hits for it and for the sessions list; `queries/run-sql.query.ts` and `queries/read-schema.query.ts` are SQL and the schema; `queries/list-pool-models.query.ts` is the models of a pool's prices, which the admission module answers machines.
4. `04-infrastructure/persistence/clickhouse/`: `clickhouse-requests.repository.ts` implements the repository over `client.ts`, `schema.ts` and `mappers/*.mapper.ts`, `clickhouse-request-log-reader.ts` the reader, `clickhouse-session-titles.ts` the titles and `clickhouse-sql-console.ts` the SQL console, which makes and checks the SQL user and reads answers with `sql-answer.ts`, each with its `*.clickhouse.test.ts` beside it. `04-infrastructure/prices/prices.ts` implements `Prices` and `PricedModels`, and `04-infrastructure/transcripts/` the port `Transcripts` (`02-application/interfaces/transcripts.ts`): one renderer per protocol, whose laws are `transcripts.laws.test.ts` there.
5. `05-tests/fakes/`: the in-memory repository, reader and titles, a scripted SQL console, and the fake of `RecordRequest` that the whole-hub harness (`shared/05-tests/harness.ts`) uses; it also gives the traffic queries and the sessions' over the in-memory reader, which reads what the fake recorded. `05-tests/traffic.ts` generates request logs and questions for the laws, `05-tests/sessions.ts` sessions, logs whose requests carry conversations, and reports, and the reader's ClickHouse test asks both readers them (the api spec's H9); `05-tests/search.ts` holds what the search laws share, and `clickhouse-search.clickhouse.test.ts` holds the search spec's words and index to ClickHouse's (K6, K7).
6. `module.ts`: the module's layer, the commands and the queries over the ClickHouse repository, reader, titles, SQL console and price lists; `traffic`, the traffic queries over any reader; `sessions`, the queries of the sessions, requests and search groups and the reporting of titles, over any reader, titles and renderers; `sql`, the SQL queries over any SQL console; `modelNames`, the names of the price lists' models, which `hub.ts` gives the display-names module; `poolModels`, the query `ListPoolModels` over the price lists, which `hub.ts` gives the admission module; and `api`, the handlers of the `traffic`, `sessions`, `requests`, `search` and `sql` groups. `main.ts` provides the layer to the hub and `hub.ts` the handlers; the relay's provider adapter calls `RecordRequest`.
7. `01-presentation/`: `traffic.api.ts`, `sessions.api.ts`, `requests.api.ts`, `search.api.ts` and `sql.api.ts`, each group's endpoints and wire Schemas; `filters.ts`, the query parameters every reading endpoint shares; `problems.ts`, the module's problems; `traffic.handlers.ts`, `sessions.handlers.ts`, `requests.handlers.ts`, `search.handlers.ts` and `sql.handlers.ts`; and the contract tests beside them.

`modules/sign-in` and `modules/display-names` show a module whose rows live in the hub store: a port in `02-application/interfaces/`, its SQLite adapter and steps in `04-infrastructure/persistence/sqlite/`, its in-memory fake in `05-tests/fakes/`, and its laws run over both. `display-names` is the smaller of the two.

The relay's `01-presentation/relay.routes.ts` shows a module's own routes beside the API, turning HTTP into a call to `ForwardRequest` and its answer back into HTTP. The relay also shows a domain shared by its port and its use cases: the `Protocol` port (`02-application/interfaces/protocol.ts`) speaks in the values of `03-domain` (`client-request.ts`, `description.ts`, `reading.ts`, `refusal.ts`), and its `module.ts` provides everything the relay owns, from `Fallback` to the `Protocols` registry and the HTTP client.

To add:

- **A command or query**: `02-application/commands/<verb-noun>.command.ts` or `queries/<noun>.query.ts`, exporting a `Context.Service` keyed `@cota/hub/<module>/<Name>` whose `execute` is an `Effect.fn("<Name>.execute")`, and a `layer` that yields the ports it needs. Provide it in `module.ts`.
- **A port and its adapter**: the port is a `Context.Service` in `02-application/interfaces/`, in the module's terms. The adapter is a `Layer` of it in `04-infrastructure/`, provided by `module.ts`. A fake for tests goes in `05-tests/fakes/`.
- **A value or rule** that a module's commands, queries or ports share: a file in its `03-domain`, named for the concept, never a loose file in `02-application`.
- **A second persistence**: a folder beside `modules/request-log/04-infrastructure/persistence/clickhouse/` whose repository provides `RequestsRepository` and honours the request log spec's "The repository", and whose reader provides `RequestLogReader` and answers as the in-memory one does (run the H9 test against it); then the lines of `module.ts` that provide the ClickHouse ones, and the connection in `config/`.
- **A reading query**: its method on `RequestLogReader`, in the module's terms; the same answer in plain code in `05-tests/fakes/in-memory-request-log-reader.ts` and in SQL in `clickhouse-request-log-reader.ts`, every value a caller gives a bound parameter, made by `ClickHouse.Param` (`string`, `strings`, `integer`, `integers`, `uuid`), which writes it as ClickHouse reads parameters; its call in the H9 test's `answersOf` (or `sessionsOf`, for what a session's reads need) and the generators it needs in `05-tests/traffic.ts` or `sessions.ts`; then the query in `02-application/queries/` and its laws over the in-memory reader.
- **A table in the hub store**: the module's port in `02-application/interfaces/`, in its own terms; its adapter in `04-infrastructure/persistence/sqlite/`, which yields `HubStore` (`shared/04-infrastructure/hub-store/hub-store.ts`) and runs its SQL through `use`; its steps (`<module>/0001-<what>`), exported beside the adapter and by `module.ts` as `steps`, and listed in `storeSteps` in `hub.ts`; and the table in the hub store spec. A released step is never edited: a change is a new step. `sign-in` and `display-names` are the examples.
- **An API endpoint**: an `HttpApiEndpoint` in the owning module's `01-presentation/<group>.api.ts` (the `sign-in` group shows one), whose params, query, headers, payload and success are Schemas (a `Schema.Record` drops a key its key Schema does not take, so check keys on the record), and whose errors are `HttpApiError.Problem` classes (`urn:cota:<name>`, with a fixed status and title) declared beside the group, or in `shared/01-presentation/problems.ts` when several groups give one. It is the owner's alone unless `.annotateMerge(mayCall("reader"))` or `mayCall("any-hub-key")` says otherwise (an owner's endpoint still says `mayCall("owner")`, or the OpenAPI document gives it no security), and it is added to the group before `.middleware(CallerMiddleware)`: only an endpoint that needs no caller comes after it. Its handler, in `<group>.handlers.ts`, calls the module's commands and queries, reads the caller from `CurrentCaller`, and turns each error into its problem with `Effect.catchTags` (`HubStoreUnavailable: hubStoreProblem`). A new group ends `.middleware(CallerMiddleware).middleware(JsonBody).middleware(HttpApiMiddleware.ProblemDetails).prefix("/api")`, is added in `api.ts`, and its handlers, `HttpApiBuilder.group(Api, "<group>", build)` exported by `module.ts`, are provided in `hub.ts`'s `api`. Then add its line to the table of who may call what, in the sign-in spec and written out in `api.contract.test.ts` (`access`), whose walker fails until both say what the endpoint declares; then `bun run openapi`, and read the diff. Its contract test, `<group>.contract.test.ts` beside it, runs `layer(Harness.layer())`: `Harness.api(headers)` is the typed client, `Harness.signIn()` gives the owner's cookie, `Harness.send` and `Harness.problemOf` check a literal problem or header, and `Harness.withTheClockRunning` answers a request that waits on the clock. `api.contract.test.ts` holds the sign-in spec's I1 to I3 and I10 and the api spec's H1 for every endpoint with no change.
- **A protocol**: a folder in `modules/relay/04-infrastructure/protocols/` exporting a `Protocol` (`02-application/interfaces/protocol.ts`), its name in `shared/03-domain/protocol-name.ts`, its entry in `shipped` (`modules/relay/04-infrastructure/protocols/protocols.ts`), its vocabulary in the scrubber's `vocabulary.ts`, its section of the protocols spec, and its exchanges in `shared/05-tests/replay/exchanges/<protocol>/`; and in the request log, its renderer in `modules/request-log/04-infrastructure/transcripts/<protocol>.ts`, listed in `renderers` (`transcripts.ts` beside it), with its rules in the sessions spec's Transcripts and its items' shapes in `05-tests/transcripts.ts`, so that T10 and T11 cover it.
- **A module**: `modules/<module>/` with the layers it has content for and a `module.ts` exporting its `layer`, which provides everything the module owns, wired in `hub.ts` or `main.ts`; its term in `CONTEXT.md` and its spec in `docs/specs`. The boundaries need no new row.

`bun run boundaries` holds the rules of ADR-0010. In a module or `shared`, `01-presentation` imports `01` to `03`, `02-application` imports `02` and `03`, `03-domain` only `03`, and `04-infrastructure` `02` to `04`. `02-application` holds only `commands/`, `queries/` and `interfaces/`, and neither it nor `03-domain` imports `effect/http`, not even a type. Another module is reached only through its `02-application/commands` and `queries`; a type two modules need moves to `shared/03-domain`. `shared` imports no module, `lib` nothing of Cota, and nothing imports `config/`, `hub.ts`, `main.ts`, `api.ts`, `restore-archive.ts` or `import.ts`. Imports are `#<path under src>` or `./`, never `..`. Tests, `05-tests`, `module.ts` and the composition root (`config/`, `hub.ts`, `main.ts`, `api.ts`, and the scripts `restore-archive.ts` of `bun run archive:restore` and `import.ts` of `bun run import`) are exempt.

## Every change

- **Vocabulary first.** A new domain concept gets its term in `CONTEXT.md` before it gets a type, a table, a route or a screen. Code, copy and docs use that one word.
- **The spec moves with the behaviour.** A change in behaviour updates the concept's spec in `docs/specs` and its `last_verified` date in the same commit.
- **The domain has no IO.** Every `03-domain` folder, a module's or `shared`'s, is Effect: a concept with state is a `Context.Service` with a `layer`, and time comes from the clock (`DateTime.now`), never from an argument. From `effect` it imports only the modules `tooling/boundaries.ts` lists, none of which reaches outside the process, and no other outside package; its tests are exempt. IO is a port in `02-application/interfaces` and an adapter in `04-infrastructure`. `bun run boundaries` fails otherwise.
- **Effect is written as generators.** `Effect.gen` and a named `Effect.fn` with early returns. A `pipe` wraps a finished effect (a retry, a timeout, a provided layer); it does not carry the logic.
- **Validate at the boundary, trust inside.** Untrusted input is decoded once with a Schema where it enters. Code past that point takes the decoded type and does not check it again.
- **No comments in code.** The exceptions are:
  - behaviour forced by something we cannot change: a provider, a client, a library, a platform or a protocol;
  - a doc comment that states a law or a public contract in one plain sentence;
  - a link to an issue, RFC or ADR for a constraint the code cannot express;
  - a lint suppression, with its reason, where the rule is wrong for that line.

  A surprise in our own code is fixed by renaming, extracting or typing it. A "do not change this" becomes a type, a test or a law.
- **Tests pin behaviour.** A test calls the code the way its callers do and asserts a literal result or an observable effect. Its name is a plain sentence about behaviour. If it would still pass with every imported function returning `undefined`, rewrite it or delete it.
- **When to add a test.** State machines, calculations, time, parsing of a provider's wire format, and a bug worth pinning. Never to raise coverage.
- **A law is a promise, not a test.** A function that makes a promise for every input gets a law in its spec, a property test of the shipped code, and, where the promise is worth a proof, a model in `proofs` that the shipped code is tested against (ADR-0004). A law is never weakened to make a check pass: a failing check is a finding.
- **Versions are pinned exactly.** No `^` and no `~`. Every `effect` and `@effect/*` package moves together.
- **Commits** follow Conventional Commits and carry no agent attribution.

| `bun run verify` | All of the above, with an evidence report in `evidence/` |
| `bun run evals:design` | The design eval (`docs/specs/design-evals/spec.md`): a client builds each task in a copy with `DESIGN.md` and in one without, and a blind judge scores both against its rules. Spends a subscription; not part of `verify`, run on purpose |
| `bun run evals:memory` | One memory eval (`docs/specs/memory-evals/spec.md`): an answerer is asked each question about a request log of constructed content, in a scratch database `cota_memory_<run>` of `compose.dev.yaml`'s ClickHouse read by a hub of its own, through the memory skill's commands, and each answer is given its verdict by code; the report is written to `evals/memory/reports`. By default the scripted answerer, which runs no real client and contacts no provider. `bun run evals:memory -- --answerer claude` is a headless Claude Code on the host whose one tool runs `cota memory` in the world's machine: it spends the owner's subscription, up to `--budget-usd` (0.5) a question, and is run on purpose, never by an agent without the owner's word |
| `bun run evals:install` | One install eval (`docs/specs/install-evals/spec.md`): an installer follows `docs/install.md` in a world of clean Linux containers, a Compose project of its own named `cota-install-<run>`, and the report is written to `evals/install/reports`. By default the rehearsal, which needs Docker and a few minutes, runs no real client and contacts no provider. `bun run evals:install -- --installer claude` is a headless Claude Code on the host, with the model owner, whose only tools act in the world: it spends the owner's subscription, up to its `--budget-usd`, and is run on purpose, never by an agent without the owner's word |
