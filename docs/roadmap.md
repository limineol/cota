# Roadmap

Cota is a rewrite of a private prototype. The prototype is the reference for behaviour: everything it does, Cota does by the last milestone. Each milestone is one pull request (or a short stack), reviewed by the owner before the next starts.

## Milestones

| | Milestone | Ships | Shown working by |
| --- | --- | --- | --- |
| 0 | **Foundation** | The repository's rules and gates; the domain for fallback and quota windows; the three verification tiers running in CI | `bun run verify` |
| 1 | **Relay** | `apps/hub`: forwarding for Claude Code, Codex and OpenAI-compatible clients; hub keys; request tags; fallback applied; usage and cost read from the stream; the request log written at ingest | Recorded provider traffic replayed through the real hub against a fake provider |
| 2 | **Request log and quota** | Sessions, transcripts, search and a read-only SQL endpoint; quota readers for Anthropic, ChatGPT, Z.ai and OpenCode Go; kept logins; the daily archive; the HTTP API the dashboard reads | The same harness, plus API contract tests |
| 3 | **Dashboard** | `packages/ui` and `apps/web` on shadcn and Tailwind; `DESIGN.md` with bad and good pairs; first-run setup in the browser | Every screen as a story in both themes; design evals |
| 4 | **Client and install** | `apps/cli`: join a machine, launch clients through the hub, report session titles, `doctor`; the install prompt for coding agents | Agent install evals in a clean container |
| 5 | **Release** | The hub's image and its deployment by Compose, with an upgrade and a rollback; an import of the prototype's log; the memory skill and its evals; the docs whole, with recipes; published images, the repository made public | A fresh install from the README by an agent |
| 6 | **Reported requests** | The request log also keeps the model calls of a client that cannot be pointed at the hub, Antigravity first, as a machine's `cota` reads them from the client's own record: observed pools, the hub's intake, the request reporter and its reader, and the dashboard's reported mark | Generated records reported through a whole hub, delivered again and in any cut, stored once; the reader confirmed on Antigravity's own record |

**2a is merged**: everything in its row, with the API's contract committed as `apps/hub/openapi.json`, and its seven specs active. Machines can report session titles through the API now; `cota`, which reports them as they change, is milestone 4. **2b is built**: everything in its row. ADR-0018 decides the archive; the hub archives each ended UTC day of the request log, verified by ClickHouse before a file is named, when the configuration has `[archive]`, and archives again a day that changed; `bun run archive:restore` checks each archived day and adds back only the rows the log lacks; the `archive` spec is active.

### Milestone 3 as a stack

Milestone 3 is four pull requests, each reviewed before the next is opened on top of it.

| | Branch | Ships | Decided in |
| --- | --- | --- | --- |

| 3b | `m3b-sessions` | Sessions with filters and search; a session's timeline, segments and transcript; the request inspector; errors grouped by cause | the spec `dashboard` |
| 3c | `m3c-tools` | The SQL console, display names, the command palette, the owner's sign-ins, and quota logins shown and forgotten in the browser | the spec `dashboard` |
| 3d | `m3d-setup` | First-run setup in the browser: the owner password and the first sign-in, and no more (pools, hub keys and quota logins stay in the configuration file, ADR-0009); passkey sign-in beside the password; the design evals, run with Claude Code and with Codex when it is not there | ADR-0021; the spec `sign-in` |

3a is merged. **3b is merged**: the sessions list as one panel, with its search and filter buttons in its head, a table that sorts by its heads, and pages; a session's page with its figures, context columns, and two tabs, its conversation segment by segment in the transcript grammar and its requests as a table under role and outcome filters; the request inspector at `/requests/$id`, its figures first and then its error, output, input, tools, params, metadata and token usage in tabs; the errors screen at `/errors`, one row per cause in a table, filtered by range, outcome, pool, provider, model and client; and the overview's figures and breakdown rows as links to those lists. Laws V21 to V30 hold what the screens decide for themselves. It leaves to 3c what the roadmap gives it, the renames among them (the screens show display names but cannot change them), and two things the API does not answer yet: what the hub priced each usage class at (the inspector states only the request's cost), and a session's title beside a request (the inspector's way back says "Session").

**3c is merged**: the SQL console at `/sql`, its schema beside a toned editor, runs kept in the URL and the browser, a virtualised answer copied as TSV, and failures in words; Settings at `/settings`, with display names set and reset in place for every kind, the owner's sign-ins listed and ended, one at a time or all the others, and each pool's quota login shown in its state and forgotten after one question; and the command palette, opened anywhere with `⌘K`, `Ctrl+K`, `/` or Search, which finds the screens, the pools, the projects, models, clients and machines to filter the sessions by, and the hub's search of the sessions. Laws V31 to V38 hold what these decide for themselves. A quota login is given with the connect script (`bun run quota:connect <pool>`), never in the browser: the owner's decision, so the dashboard has no field for a login, a token or a key, and Settings shows the command and where to run it. What the API does not answer, and the screens therefore leave out: a sign-in's address or place (the hub records its user agent and times, so a sign-in is named by its browser and system); saved SQL (there is no store for it: the console keeps this browser's last runs and the URL keeps the SQL); more than 100 values of a dimension, so the display names cannot count an id past them and the palette offers at most 100 of each kind, over the last 7 days; display names set several at once (the hub takes one at a time); and session titles as they are typed, which the prototype matched among its latest 2,000 (`GET /api/titles`): the palette asks the hub's search after a pause, which finds the words of a conversation, not of a title. 3b's two remain: what the hub priced each usage class at, and a session's title beside a request.

**3d is merged**, with its setup, its passkeys and the design evals. The hub is set up in the browser: a hub with no owner password prints a setup code in its log, and the Setup screen at `/setup` shows that line, takes the code as it is typed and the owner password chosen, and signs the owner in. The hub keeps the owner password as an argon2id hash, and makes, lists and removes passkeys, which sign in beside the password or, with the password turned off, alone; it never removes the last way in (ADR-0021). The sign-in screen asks the hub how the owner signs in and offers only what works in this browser at this address; Settings → Sign-ins shows where the owner password is kept, changes, sets or turns it off, and lists, adds and removes passkeys, never offering the last way in for removal. Laws V39 to V42 hold what these screens decide for themselves. What the API does not answer, and the screens therefore leave out: where a hub's passkeys were made, before anyone is signed in, so a sign-in screen that cannot use a passkey here says what kind of address one needs, not which.

**The design evals** are in `evals/design` (the design evals spec): `bun run evals:design` has Claude Code, or Codex where it is missing, build each of four screens the dashboard does not have (the hub keys, a pool's page, a model's price, a machine's day) in a scratch copy of the repository as it is and in one as if `DESIGN.md` had never been written; it scores each run by the check, the design lint and its stories, has a judge blind to the arm say for each of `DESIGN.md`'s rules whether the run followed it, and writes a report in `evals/design/reports` that says which rules the document changed, which the lint holds anyway, and which it changed nothing about. A first run (`evals/design/reports/2026-11-17-claude-claude-sonnet-5-5.md`: the pool's page, both arms, once, Claude Code at `claude-sonnet-5-5`; $2.51 and 12 minutes of runs, $0.51 of judging) proved the path, and found that macOS's nightly cleaning of the temporary directory could empty a copy's dependencies in the middle of a run, which the harness now prevents; its patches were scored again in fresh copies and judged again. Both pass the check; the with run's stories fail on a play function of its own that expects a figure its screen does not write, which it could not see because its dependencies were gone. With one run an arm it shows nothing about the rules yet. The full set is run on purpose, not by `verify`.

### Milestone 4 as a stack

Milestone 4 is four pull requests, each reviewed before the next is opened on top of it. Its design (ADR-0022, ADR-0023, and the `routes` and `cli` specs in draft) leads 4a's pull request.

| | Branch | Ships | Decided in |
| --- | --- | --- | --- |
| 4a | `m4a-routes` | The hub's side: routes in the hub store, each client's ordered list and default pool; `GET /api/routes`, `PUT /api/routes/{client}`, and `GET /api/route`, which answers one launch; `GET /api/machine`, what a hub key is and the pools it opens, with the keyed pools' model facts; the price lists' context and output limits; Settings → Routes | ADR-0023; the spec `routes`, and its changes to `api`, `sign-in`, `hub-store` and `dashboard` |
| 4b | `m4b-client` | `apps/cli`: `cota join` and `leave`; the launcher and the shims, with the route, the override, the bypass, machine logins and going direct; configuring Codex, OpenCode and Pi; `cota doctor`; on macOS, Linux and Windows | ADR-0022; the spec `cli` |
| 4c | `m4c-install` | The title reporter and its schedule on the three systems; the install prompt | ADR-0022; the spec `title-reporter` (`docs/specs/title-reporter/spec.md`) |
| 4d | `m4d-install-evals` | The install evals: an installer following the prompt in a world of clean Linux containers, judged by criteria from the prompt's Done and Never; the rehearsal, a scripted installer; Claude Code as the installer, with a model as the owner | the spec `install-evals` (`docs/specs/install-evals/spec.md`) |

**4a is built**: everything in its row. The hub keeps each routed client's routes and default pool in the hub store (the `routes` module and spec, laws N1 to N11), refuses a list with a shadowed route, a pattern that is not one or a pool that does not fit, stores a list whole only from the revision it was read at, and answers one launch at a time with `GET /api/route`; `GET /api/machine` tells a hub key what it is and the pools it opens, with the keyed pools' models, their context and output limits and image input from the price lists. Settings → Routes at `/settings/routes` lists one client's routes at a time, edits them in place (a pattern, its pool, moved up or down, removed or added, and the default pool) and saves them whole, says each refusal on its row and a change from another browser in the foot, and asks the hub which pool a project bills; the command palette goes to it. Laws V43 to V46 hold what it decides for itself. What the API does not answer, and the screen therefore reads elsewhere: why a stored pool no longer fits (the list says only that it does not, so the screen tells a pool gone from one of another protocol by `GET /api/pools`), and which route a `route-pool-gone` names (its detail says it in ids, so the screen shows the detail as the hub wrote it).

**4b is built**: everything in its row, in `apps/cli` (ADR-0022, the `cli` spec, now active). `cota join` shows each hub key to the hub and writes the machine's configuration and keys all or nothing, installs the shims and puts them first on `PATH` (a shell's last line, fish's own file, or the user's `Path` on Windows), configures the installed clients and ends with doctor; `cota leave` undoes it, removing only what is `cota`'s from each file. A launch, by a shim or `cota <client>`, asks the hub which pool the project bills, gives Claude Code and Codex the login that pool spends (a machine login for another Claude subscription, kept with `cota login`), tags every request, and goes direct by the last answer kept when the hub cannot be reached; `cota route` says what a launch would bill. `cota configure` rewrites Codex's `config.toml`, OpenCode's `opencode.json` and Pi's `models.json`, changing nothing of the owner's, with each keyed pool's models as its provider lists them and the hub prices them; `cota routes show` and `set` read and replace a client's routes from a terminal, signed in as the owner; `cota doctor` runs eleven checks, each failed one with its fix. Laws J1 to J10 and J14 to J18 hold its rules. The parts only Windows runs are built and their pure parts tested, but none was run on Windows: ADR-0022 lists what must be tried there. The title reporter, `cota titles`, is 4c's.

**4c is merged**: the title reporter (the `title-reporter` spec, now active, laws J11 to J13). `cota titles report` reads what Claude Code's transcripts, Codex's session index and T3 Code's database say of each session, on from where its last run stopped, and sends the hub each title that changed, in batches, keeping what the hub did not keep for the next run; `cota titles schedule` runs it every 30 seconds by launchd, a systemd user timer or Task Scheduler, `cota join` schedules it and `cota leave` removes it, and doctor's twelfth check, `titles`, says whether it is scheduled, ran lately and last ran without a problem. The install prompt, [`docs/install.md`](install.md), is written: what a coding agent asks the owner, then the hub, each machine and the routes, each step with its command, what success prints and what to do on each failure. The Windows task and systemd timer are built and their definitions tested, but neither was run on its system.

**4d is built.** The install evals are in `evals/install` (the `install-evals` spec, laws E1 to E5). One eval makes a world of its own, a Compose project named `cota-install-<run>`: a clean Ubuntu container for each machine of its task (Bun, `git`, `curl`, `openssl`, `cron`, a user without root, the owner's files, a checkout, and stand-ins for Claude Code and Codex), a ClickHouse the owner runs already, and a fake provider that answers at the providers' own names. An installer follows `docs/install.md` there, a scripted owner answering it and doing the owner's steps with fakes, and the eval reads seven criteria from the prompt's Done and Never: it ended, doctor passes on every machine, each launch's request is in the request log with its project and the pool its route names, each title arrives by the reporter's own schedule, the routes are those asked for, no secret is in a command or anything printed, and nothing of the owner's changed but Cota's part. The rehearsal, a scripted installer that takes each command from the prompt's own blocks and fails on one it does not know, passes them with two machines in about a minute and a half (`bun run evals:install`): the first time `cota` ran on Linux, and it joined, launched through its shims, configured Codex and reported titles there as on macOS. Following the prompt as written, it found three things, each fixed in the prompt: `cota route` was given by a path relative to the checkout but run in a project's directory; a join on a system without a scheduler (a container, WSL) says so on stderr while doctor passes for five minutes, so the prompt now has the owner add the crontab line at the join; and a ClickHouse the owner already runs had no word on where its password goes. A coding agent is the installer too, under the owner's choice of 2026-11-18: a headless Claude Code on the host with the login it already has (`bun run evals:install -- --installer claude`), whose only tools are a command in one of the world's machines and a message to the owner, served by an MCP server of the harness's. It is started with no built-in tool, runs in an empty directory, is asked what it has before it is given the task and refused if it has anything else (E3), and is stopped at 30 minutes, a turn limit and a spend limit, each a failed `ended` that names it (E4); it is done only when its last message begins with the word that says so (E5). A small model plays the owner, choosing the owner's steps, which stay code with fakes. Five runs cost $0.66 in all: two failed on the eval's own model owner, each fixed; the third passed every criterion; the fourth set everything up but never asked the owner to launch a client, which is the agent's; the fifth, the first under E5, passed every criterion. The first four ran before E5, and under it runs 1, 2 and 4 would also have failed `ended`. The second found that no step of the prompt built the dashboard whose Setup screen the owner opens; the prompt now builds it. Not shown: a Codex installer (the spec says what it would need), or how often Claude Code passes.

Routes were taken by default: the owner was asked on 2026-11-17 how a project is scoped to its subscriptions, and ADR-0023 records the default answer, the hub's ordered routes, which the owner can still change.

### Milestone 5 as a stack

So a real way to run the hub comes first, then the import of the prototype's history, then the change itself, and the rest after. Its design (ADR-0024, ADR-0025, and the `deployment` and `import` specs in draft) leads 5a's pull request. Each pull request is reviewed before the next is opened on top of it.

**5b, the import.** Built: `bun run import` (`apps/hub/src/import.ts`, `docs/import.md` for the owner) in the request-log module: the rules that build the request log's rows from the source's (`03-domain/import.ts`), the import source port and its adapters for the prototype's ClickHouse and its dashboard's files, the two source forms, and the restore's session reused, with a ten-minute session for an import and a dry run that adds to temporary tables of its own, so that its counts are a real run's. Laws Z5, Z6, Z8, Z9, Z12 and Z13 are property tests; Z1 to Z4, Z6 to Z8, Z10 and Z11 are of the ClickHouse tier, against a constructed source read through a user that can only select; each has a mutant. Measured once, on a constructed day of 2.8 GiB of item content (the import spec, Memory). The dry run of the real source and then the import were run on the owner's go, on 2026-11-19 and 2026-11-21: every day was added, each with the source's count of requests. The dry run found two defects no constructed day had: a page with thousands of requests passed ClickHouse's limit for a URL field, and a check on the request log's ClickHouse was stopped at 30 seconds on a busy machine. Both are fixed, the first held by Z6 and the second by a test of the session's limits.

**5c, the change.** Done on 2026-11-21, on the owner's go at each step: the deployment brought up beside the prototype, the prototype's history imported, each machine joined and its sessions moved, then the prototype's gateway stopped and its last day imported. The prototype's data is kept, as the way back.

**5d, the memory skill.** The request log is the record of every session on every machine; the memory skill is what lets an agent use it as memory: a skill, written for coding agents, that says how to find a past session by what was said in it (search), read its transcript, and ask the request log anything in SQL, with a reader key and nothing else. Its evals ask agents questions whose answers are in a request log of known content, and score what they found.

Built (ADR-0026, the specs `memory-skill` and `memory-evals`): the skill, `skills/cota-memory/SKILL.md`; `cota memory` (`key`, which keeps the machine's reader key in `hub-keys/reader`, and `get`, `sql` and `transcript`, which read the request log with it, a transcript a page at a time, so the agent never handles the key), O1 to O3 with their mutants; the memory evals' world (a scratch database of `compose.dev.yaml`'s ClickHouse holding eleven constructed sessions, a hub reading it, a machine keeping its reader key), nine questions with their facts, the answerer's port, the scripted answerer, which takes every command from the skill's own blocks, the verdicts by code (O4 to O6), the report and `bun run evals:memory`, and the scripted run in the slow tier (O9), where it gives all nine questions their right verdicts. The agent answerer, a headless Claude Code whose one tool runs `cota memory` in the world's machine under the install evals' three guards, is built as far as a stand-in client tests it (O7, O8). Waits on the owner: a run of the agent answerer, which spends the subscription (the evals spec's estimate is $0.30 to $1 a run); how the skill reaches a machine's clients, which is a copy by the owner for now; and whether `cota join` should take a reader key.

**5e, the docs.** Milestones 1 to 4 grew the README one section at a time. 5e writes the docs whole, for an owner and not for the rewrite: what Cota is, installing (the install prompt), operating a deployment (its logs, its health, the archive and a restore), upgrading and going back, and the recipes ADR-0024 leaves to the owner, each of which Cota documents and never runs. Built: the README, whole, for a stranger (what Cota is and who it is for, what the dashboard shows, what it does, the install prompt, what it needs, what it does with logins and secrets, the docs' map, how it is verified, and what has been run where); `docs/operating.md`, a deployment day to day; `docs/upgrading.md`, the deployment spec's upgrade and rollback as the owner follows them; four recipes in `docs/recipes` (HTTPS behind Caddy or nginx, the hub on a private network, copying the hub directory to another machine, a usage monitor beside the hub); `docs/verification.md` and `docs/development.md`, where the README's account of the gates and its hub run from a checkout went; and `CONTRIBUTING.md` and `SECURITY.md`. Each recipe was read against a deployment of its own, under a Compose project `cota-docs-<run>`, on macOS with OrbStack, and says how. That reading found that nginx's defaults fail the hub four ways (a request over 1 MiB, a streamed answer held until it ends, a first byte later than a minute, and a sign-in cookie without `Secure`) where Caddy's fail none; and that under OrbStack a hub published on an address the machine does not have starts healthy and answers nowhere, so ADR-0024's `docker compose up -d` publishes it again only with `--force-recreate`. Not run: a certificate from a public authority, a real VPN, two machines, Docker Desktop and Linux.

**5f, the release.** The hub image published for both platforms and the `cota` binaries for the five systems of ADR-0022, the repository made public, and the milestone's proof: an agent given only the README installs Cota from nothing. Each of these is public, and so the owner's to start, step by step. The repository is public since 2026-11-21, as one commit of the tree as it stood; [Cota 0.1.0](https://github.com/limineol/cota/releases/tag/v0.1.0), the first release, is published since 2026-11-21, and the install and the upgrade take the latest release since ADR-0028.

Built, and run for `v0.1.0`: the release (ADR-0027). `.github/workflows/release.yml` runs on a tag `v<version>` on a commit of `main`, and on nothing else: it checks the tag against the version and `main`, builds `cota` for the five systems and starts each on a runner of its own system, pushes the hub image for both platforms as `ghcr.io/limineol/cota-hub:<version>`, attests the downloads and the image with GitHub's build provenance, and makes the GitHub release last, with the release notes, the binaries, `SHA256SUMS`, `compose.yaml` and `cota.toml`. The binaries' half is `.github/workflows/binaries.yml`, which CI runs on every pull request. Cota has one version, `0.1.0`, in both manifests and the Dockerfile, and its release notes are `docs/releases/0.1.0.md`; `tooling/release.test.ts` fails a version moved without its notes or in one place only. The tag `v0.1.0` was pushed on 2026-11-21 and every job passed; what was checked of the release afterwards is in ADR-0027. Built after it (ADR-0028): the install prompt and the upgrade guide take the latest release, whose version a line of theirs finds once by GitHub's `releases/latest`: the hub's machine downloads `compose.yaml` and `cota.toml`, checks them against `SHA256SUMS`, pulls the image and names it in `.env` by tag and digest; each machine downloads its system's `cota`, checked the same way, with no Git, Bun or checkout; a build of your own is a recipe. ## New in Cota

- Setup without editing files by hand: first-run screens, and an install prompt an agent can follow (3, 4).
- A Windows client (4).
- Routes kept on the hub, so every machine agrees on which project bills which pool (4). Subscriptions by purpose, once a decided feature without a milestone, are routes: an employer's subscription is a pool only the routes of that employer's projects name (ADR-0023).

## Decided, not yet placed

Features the owner has decided on. Each gets a milestone when it is planned in detail.

- **Load balancing.** Several subscriptions with one provider share the requests between them, where today one is spent until the provider refuses it and its fallback pool takes over. Fallback becomes the in-order case of the same thing. This is where the owner's "account" (one subscription) and "pool" (a group of them) get their meanings; see the flagged ambiguity in `CONTEXT.md`. An observed pool (6) is one sign-in, never shared between, so load balancing leaves it out.
- **Rooms.** The agents working through the hub talk to each other in rooms. "Room" and "message" are kept for this: a conversation stays what one client has with one provider.
- **Codex over a WebSocket.** Codex speaks Responses over a WebSocket to OpenAI's own provider and over HTTP through the hub, which refuses an upgrade (ADR-0006). Relaying the WebSocket means reading frames in both directions, diverting a refused login on an open connection, and storing a conversation whose requests carry only what is new. It is measured first: the same Codex session direct and through the hub. A reported request's conversation is already built from the request before it and what is new (ADR-0029), which is the rule such requests would need.

## After parity

Wishes recorded while the prototype was in use. None is planned until the parity table is done.

- A forecast of when each pool empties, projected from recent requests and not from the average since the window started. It brings back "ahead of pace, but will last".
- Headroom: whether a window in reserve would still last at a faster rate, such as a client's fast mode.
- Diverting on a full quota window, not only on a refusal.
- A warning before a kept login expires.
- A one-line summary per session, always searchable.
- Clients that are out of date, flagged from their user agents.
- A colour picker for pools.
