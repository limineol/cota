# ADR-0022: One command, `cota`, joins a machine and launches its clients through the hub

## Context

The hub forwards what a client sends it (ADR-0006), but a client sends it nothing until the machine it runs on is told where the hub is, which hub key to present, which pool a project bills, and which login spends that pool. The roadmap gives that to milestone 4: `apps/cli` joins a machine, launches clients through the hub, reports session titles and runs `doctor`, with an install prompt a coding agent can follow.

The prototype's machine side is four files, copied to every machine by a sync script:

- a POSIX shell shim, installed as `claude`, `codex`, `opencode` and `pi` in a directory a line at the end of `~/.zshrc` or `~/.bashrc` puts first on `PATH`. It learns its client from its own name, drops its directory from `PATH`, reads the project from the `origin` remote (`owner/repo`, lowercased, without `.git`) or the directory's name, and `exec`s the real client with the hub's address and the tags. Which subscription Claude Code spends is a `case` on the repository's owner, written in the shim; one environment variable overrides it and another bypasses the hub. It waits for the hub's `/health` up to a deadline (5 seconds, 40 for a work subscription, because a harness resumes its threads after a reboot before the private network is up, within the minute the Agent SDK gives Claude Code to start), and past it goes direct with one line on stderr. For a subscription other than the one Claude Code is signed in to it exports a `claude setup-token` token kept in a file, and refuses to start without it;
- an install script that writes the hub's address and two hub keys (read from stdin) to a directory only the user can read;
- a Python script that writes a `hub` provider into OpenCode's, Pi's and Codex's configuration files, with the hub's model list enriched from models.dev, and removes or disables the providers that go around the hub;
- a Python script, run every 30 seconds by launchd or a systemd user timer, that reads Claude Code's, Codex's and T3 Code's session titles incrementally and sends the ones that changed.

It runs on macOS and Linux. On Windows only the configuration step runs: no shim, no tags, no titles. Nothing diagnoses a machine but the shim's stderr lines and an error file. Python and the scripts shell out to `curl` for every call, because macOS keeps a program it cannot ask for permission, such as a Python from a version manager, off the local network when a launchd job runs it.

Three facts of Cota shape the answer. A subscription hub key rides in the environment of every command a client runs, so it spends nothing without a login and reads nothing (ADR-0012, the admission spec's A1 to A6). The pool is in the path (ADR-0006), so whatever starts a client chooses the pool. And routes are kept on the hub (ADR-0023), so a machine asks rather than decides.

## Decision

**One binary, `cota`, in `apps/cli`.** TypeScript and Effect 4 on Bun, as the rest of the repository (ADR-0002, ADR-0003), with the rules that have no IO in a `03-domain` held by laws, and the file system, processes, the clock and the hub behind ports (ADR-0010's layers, where a command-line program has them; `tooling/boundaries.ts` gains its rows). `bun build --compile` makes one file per system: macOS on arm64 and x64, Linux on x64 and arm64, Windows on x64. In milestone 4 it is built from a checkout (`bun run cli:build`); publishing it is milestone 5's. It calls the hub through the typed client of `@cota/hub/api`, as the dashboard does, and the relay only where a client would (a pool's model listing). The behaviour, the commands and the laws are `docs/specs/cli/spec.md`.

**What `cota` is not.** It is not a proxy: a launched client talks to the hub itself. It is not a daemon: nothing of it keeps running but a launched client's parent where it cannot replace itself with the client (below), and the title reporter, which runs and ends. It never contacts a provider, never reads a client's own login, and never holds a held key or a quota login. The one login it keeps is a **machine login** (`CONTEXT.md`): a `claude setup-token` login for a Claude subscription other than the one Claude Code is signed in to on that machine, given with `cota login <pool>`. It uses no keychain in milestone 4: its secrets are files only the user can read, as the prototype's were.

> Amended by ADR-0029: the request reporter (`cota requests report`), which reports the model calls of the clients that cannot be launched through the hub, also runs and ends, scheduled as the title reporter is; its state (`requests.json`, `requests.error`) is in the state's directory beside the title reporter's, and the data folders it reads and the observed pool each bills are in `config.toml`.

**The machine's files.** Written whole and atomically (a file beside the target, then a rename), with the modes below on macOS and Linux. On Windows the files inherit the user profile's permissions, which give the user, the administrators and the system access, and no one else.

| What | macOS and Linux | Windows | Mode |
| --- | --- | --- | --- |
| The configuration, `config.toml` | `$XDG_CONFIG_HOME/cota`, default `~/.config/cota` | `%APPDATA%\cota` | directory 0700, file 0600 |
| Hub keys, `hub-keys/subscription` and `hub-keys/keyed` | the configuration's directory | the same | 0600 |
| Machine logins, `logins/<pool>` | the configuration's directory | the same | 0600 |
| State: the last route answers (`routes.json`), the title reporter's (`titles.json`, `titles.error`) | `$XDG_STATE_HOME/cota`, default `~/.local/state/cota` | `%LOCALAPPDATA%\cota\state` | directory 0700, files 0600 |
| Shims | `$XDG_DATA_HOME/cota/bin`, default `~/.local/share/cota/bin` | `%LOCALAPPDATA%\cota\bin` | 0755 |

macOS uses the XDG defaults, not `~/Library`, as the clients themselves do. The configuration holds no secret:

```toml
hub = "http://cota.internal:8080"
machine = "studio"

[launch]
wait = "5 seconds"
wait_routed = "40 seconds"

[clients.claude-code]
own_pool = "personal"
```

**Secrets never on a command line.** Hub keys and machine logins are read from standard input when it is not a terminal, else from a prompt that does not echo; never from an argument, which every user of the machine can list. They are never printed, logged or put in a problem. A secret leaves its file only for the environment of a client `cota` launches, and for the configuration files of the clients that cannot read it from anywhere else (Codex, below). The owner password, which `cota routes` needs to change routes, is `COTA_OWNER_PASSWORD` or a prompt, as the connect script reads it.

**Joining.** `cota join <hub> [--machine <name>] [--no-shims] [--allow-plain-http]` reads hub keys, one a line, and asks the hub what each is (`GET /api/machine`, any hub key, ADR-0023 lists it): a key the hub does not know, a reader key (it opens no pool), or two keys of one scope stop the join, which then writes nothing, so a machine keeps at most two: one subscription key and one keyed. It keeps the hub's address and the machine's name (the host name's first label, lowercased, unless `--machine` names one), and each key under its scope. An `http` address that is not loopback needs `--allow-plain-http`, kept in the configuration, because every request then carries a hub key in the clear. It then installs the shims and their `PATH` line (unless `--no-shims`), configures the clients that read a configuration file and are installed (their command is on `PATH` or their configuration directory exists), schedules the title reporter and runs it once, and runs doctor. Joining again with the same answers changes nothing; with others it replaces them. `cota leave` undoes every step: the shims and their line, `cota`'s part of each client's configuration, the schedule, and the machine's files.

**The launcher.** `cota <client> [args…]` (`claude`, `codex`, `opencode`, `pi`), or a shim of the same name, launches the client in these steps:

1. **The bypass.** With `COTA=off`, or on a machine that has not joined, the real client is started with the environment and arguments it was given, untouched.
2. **The real client** is the first file of its name on `PATH` that is not in the shims' directory and is not a shim of `cota`'s; `PATH` without the shims' directory is what the client is given, so a client that runs another reaches it directly, and no launch loops. None: the launch stops (exit 127) and says the client is not installed.
3. **The project** is `COTA_PROJECT` when it is set, so a harness or a parent launch can name it. Else it is read from the `origin` remote of the repository holding the working directory, in any of its forms (`https://host/owner/repo.git`, `ssh://git@host:22/owner/repo`, `git@host:owner/repo.git`, with or without user information, a port, `.git`, a trailing slash): the path after the host, without `.git`, lowercased, and never the user information, which can hold a token. A remote that is a local path, and a directory outside a repository, give the directory's name. `COTA_PROJECT` is set to it for the client.
4. **The pool**, for Claude Code and Codex, is the override (`COTA_POOL`, or `cota --pool <pool> <client>`) or the route, both answered by the hub: `GET /api/route?client=…&project=…[&pool=…]` (ADR-0023), with the machine's subscription hub key, or its keyed one when it has no other. The answer says the pool's id, kind, protocol and provider, and why (a route, the default pool, the override). It is asked once a second until it is answered or the launch's deadline passes: `wait` (5 seconds), or `wait_routed` (40 seconds) when the last answer kept for this client and project named a pool other than the client's own, as the prototype waited longer for a work subscription. The answer is kept (`routes.json`), one per client and project, the latest 1,000.
5. **The login**, for Claude Code and Codex, follows the pool's kind. A subscription pool that is the client's **own pool** (the configuration's `own_pool`, else the client's default pool as the hub answers it) is spent with the client's own login. Another subscription pool is spent with the machine's machine login for it; without one the launch stops, says which pool the project bills and how to make a machine login, and starts nothing: spending the client's own login there would bill one subscription and record another. A keyed pool is spent with the machine's keyed hub key; without one the launch stops.
6. **The environment** is set as the client's section below says, and nothing else of the client's is changed.
7. **The start.** On macOS and Linux `cota` replaces itself with the client (`execve`), so the client is the process its parent started, with its signals, its terminal and its exit status. Where Bun cannot do that, and on Windows, which has no such call, `cota` starts the client as its child with the same standard streams, ignores the interrupts the terminal sends to both, forwards the termination signals it receives, and exits with the client's status (128 plus the signal's number for a client killed by one).

**When the hub cannot be reached** by the deadline, the launch **goes direct**, with one line on stderr naming the hub and what is lost (`cota: http://cota.internal:8080 cannot be reached; claude goes direct with personal's login, unlogged and with no fallback.`), on the last answer kept for its client and project: its own login for its own pool, the machine login for another subscription pool, and a stop for a keyed pool, whose held key only the hub has, or for a pool whose login the machine lacks. With no answer kept for that project, it goes direct with the client's own login, and the line says the route is unknown. A hub that answers, but cannot say the route (its store failed), is not unreachable: the launch goes through the hub on the kept answer, and stops without one.

**Claude Code** (`claude`, client `claude-code`, routes to pools of `anthropic-messages`):

- `ANTHROPIC_BASE_URL={hub}/pools/<pool>`, and `ANTHROPIC_CUSTOM_HEADERS` with `x-cota-project`, `x-cota-machine` and `x-cota-client: claude-code`, and, for a subscription pool, `x-cota-key: <subscription key>`, one `Name: value` a line, after any headers the owner already set there that are not `x-cota-*`.
- For a subscription pool, `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` are removed, since either would win over a login; `CLAUDE_CODE_OAUTH_TOKEN` is the machine login, or is removed for the own pool, so Claude Code spends its own `/login`.
- For a keyed pool, the keyed hub key is the client's credential, in the header the pool's provider takes its own key in, as `examples/cota.example.toml` shows: `ANTHROPIC_API_KEY` for the provider `anthropic`, otherwise `ANTHROPIC_AUTH_TOKEN` with `ANTHROPIC_API_KEY` set empty. The relay takes the hub key from that header and sends the held key in its place (the relay spec).
- `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1`, so Claude Code names its requests' purposes (the protocols spec).
- Going direct: none of the above but the login.

**Codex** (`codex`, client `codex`, routes to pools of `chatgpt-codex`): Codex is spent only with its own ChatGPT login, since `cota` keeps no machine login for ChatGPT, so a route to a ChatGPT pool other than Codex's own pool stops the launch. The launch puts `-c model_provider="cota-<pool>"` before the client's arguments and sets `COTA_PROJECT`; the provider's table, with the hub key and the other tags, is in Codex's own configuration (below), which the launch writes first when the routed pool's table is missing. Going direct: no `-c`, so Codex uses its own provider.

**OpenCode and Pi** (`opencode`, `pi`): their pools are chosen by the model the person picks, among the providers `cota` writes into their configuration, one per keyed pool (ADR-0006), so they have no route and no override. The launch sets `COTA_PROJECT`, which their configuration puts in the `x-cota-project` header, and starts them at once: nothing it sets depends on the hub, and they cannot go direct, since their pools' keys are held by the hub. A request made while the hub is down fails in the client, as in the prototype.

**Shims and `PATH`.** On macOS and Linux a shim is a POSIX shell script, `exec '<path of cota>' <client> "$@"`, with a marker line that says it is `cota`'s; on Windows it is a `.cmd` file, `@"<path of cota.exe>" <client> %*`, the form npm's own shims take. `cota join` and `cota shims` put the shims' directory first on `PATH`:

- in zsh, bash and other POSIX shells, by one marked line at the end of the shell's file (`~/.zshrc`; `~/.bashrc`, and `~/.bash_profile` where a login shell does not read `~/.bashrc`), moved back to the end whenever it is not last. Installers (OpenCode's upgrade, for one) add their own `PATH` lines at the end of the same files, and a line after ours puts its directory first. Cota keeps the prototype's rule, because no earlier file wins against a later line, but moves the line only when the owner runs `cota join` or `cota shims`, never from a launch or a scheduled job; doctor fails the check when the line is not last, or a new login shell does not find the shim first. In fish, by a file of `cota`'s own, `~/.config/fish/conf.d/cota.fish`.
- on Windows, by putting the directory first in the user's `Path` variable (through PowerShell's `[Environment]::SetEnvironmentVariable`, which tells running programs of the change; terminals already open keep their old `PATH`). Installers more often add to the end there; doctor checks the order all the same. Windows puts the machine's `Path` before the user's, so a client installed for the whole machine is found before the shims; npm installs a client for the user, in the user's `Path`, which the shims come before.

`cota <client>` always works, with or without the shims, and `--no-shims` joins without them.

**Configuring the clients that read a file** (`cota configure`, run by `join` and by a Codex launch that lacks its table). Each rewrite reads the file, replaces what is `cota`'s and only that, checks the result reads as the format (JSON or TOML, by a parser) and that what is not `cota`'s reads as the same value as before, and writes it atomically, or leaves the file as it was and says why. A rewrite with nothing to change writes nothing. `cota leave` is the rewrite with no pools. What is `cota`'s:

- **Codex**, `$CODEX_HOME/config.toml` (default `~/.codex/config.toml`), mode 0600: one table `[model_providers.cota-<pool>]` per ChatGPT pool the subscription hub key opens, written at the end of the file, each under the marker comment `# cota: this table is rewritten by cota configure.`, with `name = "OpenAI"` (Codex keys its ChatGPT features, such as compaction and web search, off that name), `base_url = "{hub}/pools/<pool>/backend-api/codex"`, `wire_api = "responses"`, `requires_openai_auth = true`, `http_headers` with `x-cota-key`, `x-cota-machine` and `x-cota-client = "codex"`, and `env_http_headers = { "x-cota-project" = "COTA_PROJECT" }`. The provider is in the file, not only in the launch's flags, because Codex saves a session's provider and finds it again only there (`codex resume`), and a desktop app that reads the file starts without the launcher's environment, so the hub key is written in the file. Every other table, `[features]` included, is the owner's: Cota reads zstd bodies (ADR-0006), so the prototype's `enable_request_compression = false` is not needed. A `cota-` provider written in another form (an inline table, dotted keys) is not rewritten: the rewrite stops and doctor names it.
- **OpenCode**, `~/.config/opencode/opencode.json`: one provider `cota-<pool>` under `provider` per keyed pool of `openai-chat` the keyed hub key opens, with `npm = "@ai-sdk/openai-compatible"`, its name (the pool's display name, else its id, with "· Cota"), `options.baseURL = "{hub}/pools/<pool>"`, `options.apiKey = "{file:<keyed key file>}"`, `options.headers` with `x-cota-machine`, `x-cota-client: opencode` and `x-cota-project: {env:COTA_PROJECT}`, and its models. Other providers, `disabled_providers` included, are the owner's: the prototype removed and disabled the providers that went around its hub; Cota leaves them. A file with comments (JSONC) is not rewritten, since a JSON writer would drop them: the rewrite stops and doctor says so.
- **Pi**, `$PI_CODING_AGENT_DIR/models.json` (default `~/.pi/agent/models.json`): one provider `cota-<pool>` under `providers` per such pool, with `baseUrl`, `api = "openai-completions"`, `apiKey` a command, `!'<cota>' hub-key keyed` with `cota`'s own path, in double quotes on Windows (Pi runs a command for a key that starts with `!`; `cota hub-key keyed` prints the keyed hub key, one form on every system), `headers` with the tags and `x-cota-project` from `COTA_PROJECT`, `compat.sendSessionAffinityHeaders = true` with the OpenAI format (the session header the providers need, the protocols spec), and its models. Pi's `settings.json` is the owner's: the prototype rewrote its `enabledModels`; Cota does not.

**The model list** of a keyed pool comes from the hub. `cota configure` asks the pool's own listing through the relay, as a client would (`GET {hub}/pools/<pool>/models` with the keyed hub key, recorded as a model listing with the client tag `cota`), and takes each listed model's name, prices, context and output limits and whether it reads images from the pool's facts in `GET /api/machine`, which come from the hub's price list for the pool and its own prices (ADR-0009). A model the price list lacks is written with its id alone; a pool whose listing fails keeps the models it was last written with, and says so. The price lists gain the limits and the image input from models.dev (`bun run prices:update`), in milestone 4a. `cota` never asks models.dev itself.

**Machine logins.** `cota login <pool>` reads a login from standard input or a prompt, asks the hub that `<pool>` is a subscription pool of `anthropic-messages` (`GET /api/machine`), and keeps it in `logins/<pool>`; `cota logout <pool>` removes it. `cota` does not try the login against Anthropic: it never contacts a provider. A login that does not work is the provider's refusal, which Claude Code shows. Its message for a missing one says how to make it: `claude setup-token`, signed in to that pool's subscription, then `cota login <pool>`.

**The title reporter.** `cota titles report` runs once and ends. It reads, from where each last run stopped (a byte offset per file; a file shorter than its offset is read again from the start; a line not yet ended is left for the next run), Claude Code's transcripts (`~/.claude/projects/*/*.jsonl`, lines of `custom-title` and `ai-title`, the owner's name winning over the generated one; a first run skips files untouched for 14 days), Codex's session index (`~/.codex/session_index.jsonl`, `id` and `thread_name`), and T3 Code's database (`~/.t3/userdata/statev2.sqlite`, read only, its thread titles winning over both, since they are what the owner sees), each where it exists. A title is trimmed and cut to 200 characters. It sends the titles that differ from the last sent for their session, in batches of at most 1,000 (`PUT /api/session-titles`, with the subscription hub key, else the keyed one, and `x-cota-machine`), and records a batch as sent only once the hub answers 204, so a failed batch is sent again by the next run. A run that fails writes why to `titles.error`, which the next good run removes; doctor reads it. `cota titles schedule` runs it every 30 seconds:

- macOS: a LaunchAgent, `~/Library/LaunchAgents/cota.titles.plist`, with `StartInterval` 30 and `RunAtLoad`. Every run on macOS sends through `/usr/bin/curl`, its whole request (the hub key among it) as curl's configuration on its standard input, until it is shown that macOS lets a launchd job of `cota` reach a hub on the local network (Facts to confirm). A run by hand sends the same way as the scheduled one, so that running it by hand tries what the schedule does.
- Linux: a systemd user service and timer, `cota-titles.service` and `cota-titles.timer`, every 30 seconds. Without a systemd user session (a container, WSL without systemd), `join` says so, and doctor's check fails with the line to add to the owner's own scheduler.
- Windows: a Task Scheduler task with two time triggers half a minute apart, each repeating every minute, its least interval; each run reports once. A run that reported, waited 30 seconds and reported again, as first decided, would keep a process waiting for nothing, and two triggers need none.

OpenCode's and Pi's titles are not reported in milestone 4. Its behaviour, its doctor check and its laws are `docs/specs/title-reporter/spec.md`.

**Doctor.** `cota doctor [--json]` runs every check and prints each with its outcome; a failed one says what is wrong and the command that fixes it, a warning what is worse than it should be. It exits 1 when a check failed, else 0. `--json` prints `{ ok, checks: [{ id, outcome, problem, fix }] }`. The checks, in order: the configuration reads; the hub answers `/health`; each hub key is known and of its scope (`GET /api/machine`); the machine's files have their modes; the shims are installed, call a `cota` that exists, and come first on `PATH` in a new login shell, and the `PATH` line is last; each client's real command is found (a warning when missing); each client's own pool, and each machine login's pool, is a pool the hub has, of the client's protocol; each configured client's file holds what `cota configure` would write now; the title reporter is scheduled, its last run was under 5 minutes ago, and `titles.error` is absent. The list, each check's id and its fix, are the CLI spec's, but for the title reporter's, which is its own spec's.

> Amended by ADR-0029: doctor's last check is the request reporter's, `requests`, which is its own spec's (`docs/specs/request-reporter/spec.md`).

**What Windows does differently**, in one place: a `.cmd` shim, and the user's `Path` in place of a shell's file; no `execve`, so `cota` waits as the client's parent; a real client installed by npm is a `.cmd`, which is started through `cmd.exe` with its arguments quoted for it (a known source of injection when arguments are not), so `cota` prefers a client's `.exe` when both exist; the machine's name from `COMPUTERNAME`; files guarded by the profile's permissions, not modes; Pi's key by `!"<cota>" hub-key keyed`, the command elsewhere's with the path in double quotes; and the title reporter's task triggered twice a minute.

**Left to milestone 5**: publishing `cota` (where, and under which npm name, is the owner's), signing it for macOS and Windows, `cota update`, and keeping a machine's clients' configuration current without the owner running `cota configure`.

> Amended by ADR-0027: publishing `cota` is a release's: the five binaries as downloads of the GitHub release of each version's tag, named for their systems, with `SHA256SUMS` and build provenance, and no npm package. Signing it for macOS and Windows, `cota update`, and keeping the clients' configuration current stay left.

> Amended by ADR-0028: a machine installs `cota` from the latest release, its system's file found from `uname -s` and `uname -m`, checked against `SHA256SUMS` and installed as `~/.local/bin/cota`, with no Bun, Git or checkout; updating it is installing another release's the same way. Building it from a checkout is the recipe of a build of your own.

### Facts to confirm when built

These were read from the prototype's code or the clients' public documentation, and no client or provider was run to see them. Each is checked by hand on a real machine when 4b is built, and recorded where the protocols spec records its facts.

- **Claude Code**: `ANTHROPIC_CUSTOM_HEADERS` is one `Name: value` a line; `ANTHROPIC_AUTH_TOKEN` and `ANTHROPIC_API_KEY` win over `CLAUDE_CODE_OAUTH_TOKEN`, which wins over the `/login` login; a `claude setup-token` login in `CLAUDE_CODE_OAUTH_TOKEN` spends its subscription; with `ANTHROPIC_API_KEY` set, an interactive Claude Code may ask once whether to use the key; where its transcripts are on Windows.
- **Codex**: `-c model_provider=<id>` selects a table of `config.toml`, before a subcommand too, and a later `-c` of the owner's wins; `http_headers`, `env_http_headers`, `requires_openai_auth` and `name = "OpenAI"` behave as the prototype relied on; `codex resume` lists only the sessions of the provider it starts with; `session_index.jsonl`'s `id` is the `session-id` header the hub reads.
- **OpenCode**: the global file's place on each system, whether it also reads an `opencode.jsonc` beside it, the `{file:…}` and `{env:…}` substitutions, and what an unset variable becomes in a header.
- **Pi**: `models.json`'s fields as the prototype wrote them; whether a header's `$NAME` is read from the environment; how a `!` command runs on Windows.
- **T3 Code**: its database's tables, which are not a public interface, and its place on Windows.
- **Bun**: how it quotes arguments for a `.cmd` on Windows. Confirmed on macOS (arm64, Bun 1.4.2, 2026-11-17): a program compiled with `bun build --compile` has Node's `process.execve`, and replaces itself with the client, which keeps `cota`'s process id, receives its signals and exits with its status; `cota` uses it on macOS and Linux and starts the client as its child where it is missing. Not yet run on Linux.
- **macOS**: whether a launchd job of `cota`, which is not Apple's, can reach a hub on the local network without the owner granting it Local Network access.
- **Windows**: Task Scheduler's least interval of one minute; that two time triggers with a fixed start in the past, each repeating every minute without end, run the task twice a minute and go on after a restart; that `schtasks /Create /XML` takes the definition `cota` writes (UTF-16 with a byte order mark); whether a scheduled console program shows a window each run, and how to keep it hidden; that a change of the user's `Path` reaches new terminals. Built in 4b but never run on Windows, each to be tried there: that `powershell.exe -NoProfile -NonInteractive -Command` with `[Environment]::GetEnvironmentVariable('Path', 'User')` and `SetEnvironmentVariable('Path', $env:COTA_USER_PATH, 'User')` reads and writes the user's `Path`, and whether that read expands the `%VAR%` entries of a `Path` kept as `REG_EXPAND_SZ` and that write keeps it `REG_SZ`, which would freeze them (if so, the adapter must read and write the registry value as it is kept, `HKCU\Environment`, without expanding); how long PowerShell takes to start, against the 5 seconds a step has no deadline for; that a `.cmd` shim, `@"<cota.exe>" <client> %*`, passes every argument through as typed; how Pi runs a `!` command on Windows (through `cmd.exe`, so that `"<cota>"` is read as one path, or another shell); where OpenCode and Codex keep their files there (`%USERPROFILE%\.config\opencode\opencode.json` and `%USERPROFILE%\.codex\config.toml` are assumed, the first ignoring `XDG_CONFIG_HOME` there).

## Alternatives weighed

- **Keep the shell shim and the Python scripts.** They work on the owner's machines today. They do not run on Windows, they need Python and `curl`, their rules (the project from a remote, the rewrite of a configuration file, reading titles incrementally) have no tests, and the routes are a `case` in a shell script. One program in the repository's language puts those rules under laws and mutants like the hub's.
- **A local proxy on each machine**, which every client would be pointed at, adding the tags and forwarding to the hub. It would tag a client started any way at all. It is a second hop for every stream, another process to keep alive on three systems, and another place for a request to fail; the hub is the proxy already.
- **Shims as copies or links of the binary**, which read the name they were started by, as the prototype's shim did. A compiled program is tens of megabytes, a copy per client is four, and whether a compiled Bun program sees the name of a link it was started through is not known. A script of a few bytes that runs `cota` is the same on every system that has a shell, and a `.cmd` is what Windows users run for every npm client already.
- **A shell shim that asks `cota` for the environment and `exec`s the client itself** (`eval "$(cota env claude)"; exec …`). It leaves no parent process where Bun cannot `execve`. It puts the environment, hub key and login included, through a shell's parser, and has no form on Windows.
- **The system's keychain** (Keychain, libsecret, Credential Manager) for hub keys and machine logins. Better at rest, but three adapters, prompts a launchd job cannot answer, and Linux machines without a secret service. Files only the user can read are what the prototype used and what the clients do with their own logins; milestone 5 can revisit it.
- **OpenCode through `OPENCODE_CONFIG`**, a file of `cota`'s that OpenCode merges, and Codex through the launch's `-c` flags only. Nothing of the owner's files would be touched. But an OpenCode started otherwise (its desktop app, an editor) would not see the hub, and Codex would not find a session's provider to resume it. The rewrites touch only what is `cota`'s, and laws hold that.
- **Removing and disabling the providers that go around the hub**, as the prototype did, so that every request of OpenCode and Pi is logged. It changes what is not `cota`'s, which no rewrite law could then promise; the owner decides which providers a client keeps.
- **Refreshing the clients' configuration from the title reporter's schedule**, as the prototype's daily sync did. The model lists would follow the hub without the owner. A job that rewrites the clients' files in the background is a surprise the owner did not ask for; doctor says when a file is behind, and `cota configure` brings it up to date.
- **Matching routes on the machine**, from a list it downloads. ADR-0023 weighs it.

## Consequences

- The hub gains `GET /api/machine` (what a hub key is and the pools it opens, with the keyed pools' model facts), `GET /api/route` and the routes of ADR-0023; the sign-in spec's table gains them, and its I2 lets a spending hub key call the two a machine needs. The price lists gain context and output limits and image input.
- Machines need no Python and no `curl`, but on macOS the scheduled reporter keeps using `/usr/bin/curl` until a launchd job of `cota` is shown to reach the local network.
- A Windows machine launches, tags, routes and reports titles, which the prototype's did not.
- Worse than the prototype: a launch asks the hub for its route, a round trip the prototype's `case` did not make, and in a project the machine has not launched in before, with the hub unreachable, the route is unknown and the client goes direct with its own login. Where Bun cannot `execve`, a parent process of a few tens of megabytes stays for each launched session. A compiled program starts in tens of milliseconds, a shell script in a few. The clients' configuration is current only when the owner runs `cota configure`, where the prototype refreshed it daily. Providers that go around the hub are left in OpenCode, and Pi's enabled models are not rewritten. OpenCode's and Pi's titles are still not reported. A launched client can still run another client directly, untagged, since the shims' directory is not on its `PATH`.
- `cota` does not give quota logins: that means reading a client's own login, which `cota` never does. The connect script (`bun run quota:connect`, ADR-0017) stays the way to give one, and a Claude quota login is still connected from macOS only.
- The install prompt and the install evals (4c) drive `cota join` and `cota doctor` in a clean container, with stand-in clients; how an agent there gets a login is the owner's to decide when 4c is designed.
